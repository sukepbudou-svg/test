# boatrace-predictor / PERRY AI プロジェクト概要

## 概要
競艇3連単予想ツール。LightGBMモデル＋複数エージェントで予想を生成し、
ローカルWeb（Flask + SQLite）に自動記録する。
ツール名: **PERRY AI**（黒船のペリーをコンセプトにしたAI予想キャラクター）

## 現在の予想設定（2026-10-16 荒れPTを2026年5月当時の配点に差し戻し）

### ラベル・参戦判定（src/model/predictor.py: _calc_race_pt）
2026-08-25〜10-16は「A/B/C/D区分・満点20点・PT_MIN_SCORE=9」の簡略版PTを使っていたが、
STATSページの「PT値別集計」「PT条件パターン別内訳」「オッズ帯別成績」いずれでも
PTの高さと実配当額・的中率に明確な相関が見られず、有効性を裏付けられなかった。
一方、約3〜5ヶ月前（2026年5月頃、4エージェント体制が固まった直後でARARE_MIN_SCORE=7
だった時期）は戦績が良かったとの実感があったため、2026-10-16に当時の配点へ差し戻した
（git履歴から commit `3e28429` 時点のロジックを復元）。
買い目の選び方（オッズ帯ブレンド方式+条件ベース5点目、下記）は当時と別物のままなので、
今回の変更で分かるのは「PTの付け方だけを変えた効果」である点に注意
（当時の好成績が選出方式とPTのどちらに起因するかは未検証のまま、との整理で合意済み）。

参戦ラインは `PT_MIN_SCORE = 7`、満点16点。

| ラベル | 条件 | 参戦 | 色 |
|--------|------|------|----|
| **神熱** | PT合計 ≥ PT_MIN_SCORE | ○ | ゴールド（#ffcc00）|
| **見送り** | PT合計 < PT_MIN_SCORE | ✗ | グレー |

**1号艇の弱点（各2点）**
| 条件 | 点数 |
|------|------|
| 1号艇展示ST遅い（≥0.18） | +2 |
| 1号艇モーター低調（2連率<0.35） | +2 |
| 1号艇B級（grade≤2） | +2 |
| 外艇(4〜6号)の展示タイムが全艇中最速 | +2 |

**補助条件（各1点）**
| 条件 | 点数 |

| 外艇(4〜6号)の展示STが速い（≤0.12・最初に該当した1艇のみ） | +1 |

| 一般戦（meet_grade_num≤1） | +1 |

> `by_prob`引数はシグネチャ互換のためだけに残っており、現在は未使用。


### 買い目選出方式（オッズ帯ブレンド方式+歪み検知5点目: strategy_version='8'のまま、実結果統計も'5'以降）
軸選出スコア（コース位置点ベース）は廃止。4エージェント合成確率（ML45%+コース戦略20%+選手成績20%+モーター15%、
predict_race内のwin_probs）をそのまま各組み合わせの確率として使い、オッズ帯ごとに選ぶ。

- **3連単（5点・オッズ帯方式、2026-10-16改訂）**:
  | 点数 | オッズ帯 | 選出方法 |
  |------|---------|---------|
  | 1〜2点目 | 100〜150倍 | 同一帯からブレンド上位2点 |
  | 3点目 | 151〜250倍 | ブレンド最大の組み合わせ |
  | 4点目 | 151〜250倍 | ブレンド最大の組み合わせ（**1号艇除外**） |
  | 5点目 | 指定なし | **歪み検知選出**（モデル確率÷市場の暗示確率が最大の組み合わせ） |
  - **選出基準は「確率×EV」のブレンド（幾何平均: √(確率×確率×オッズ)）**。2026-09-04に純粋EV
    (確率×オッズ)方式から変更。純粋EVだと帯の上限側（高オッズ側）に、純粋確率だと帯の下限側に
    選出が偏ってしまい、範囲を分割した意味が薄れる（実際、旧EV方式では100〜199倍帯の選出が
    130〜185倍あたりに偏り、100〜129倍がほぼ選ばれていなかった）。ブレンドは両者のバランスを取り、
    帯内の偏りを緩和する。約3〜5ヶ月前（2026年5月頃、荒れ条件スコア≥7時代）はまさにこのブレンド
    方式に近い選出（本命穴・超穴は確率順、最も大穴の帯だけブレンド）を使っており、バックテストROIも
    良好だった実績がある
  - **5点目は2026-10-16に一度刷新、2026-10-19に再度刷新**。旧5点目（251〜900倍・ブレンド）は
    約6週間の実績で的中率0.06%・回収率12.7%と他の帯（1〜2点目0.67%/73.1%、3〜4点目0.31%/66.0%）
    に比べ著しく機能していなかったため2026-10-16に廃止し、展示タイム・展示ST・前付け・今節成績
    から4エージェント確率を一切使わずに「脅威艇」を特定する条件ベース選出(`_pick_threat_based`/
    `_pick_condition_based_ana`、オッズ帯200〜300倍限定)に差し替えた。しかし固定2パターン
    （新本命穴・新超穴）しか候補を出さない上にオッズ帯の絞り込みも重なり、「候補なし→スキップ」
    が頻発する問題があったため、2026-10-19に**歪み検知方式(`_pick_edge_based`)**へ再度差し替え、
    条件ベースのロジック（`_pick_condition_based_ana`・`_calc_threat_score`）自体は削除した。
    歪み検知方式は、モデル確率(`prob`)と市場オッズが暗示する確率
    （`(1 - TAKEOUT_RATE_3REN) / オッズ`）の比（エッジ）が最大の組み合わせを、オッズ帯を
    区切らずレース全体から選ぶ。エッジ = `EV / (1 - TAKEOUT_RATE_3REN)` と数学的に単調な
    関係にあるため、実質的にはレース内でEVが最大の組み合わせを選んでいる点に注意
    （1〜4点目のブレンド方式と同じ「モデルが強気な場所」を狙っている）。1〜4点目で既に
    選ばれた組み合わせはスキップし次点を採用、全て選出済みならスキップ（フォールバックなし）。
    STATSページの「モデル確率 vs 市場オッズ」統計で、このエッジの大きさが実際の的中率・
    回収率と相関しているか（=本当に市場の歪みを検知できているか）を検証できる。
  - 4点目の1号艇除外は2026-08-28追加。高オッズ帯なのに1号艇が絡み続ける矛盾（構造的な
    コース優位性バイアスの影響）を避け、「1号艇が完全に不在の大荒れ」パターンを狙い撃つ目的
    （5点目は歪み検知選出のため対象外。1号艇を含む組み合わせも候補になり得る設計）
  - 既に選出済みの組み合わせは除外（重複なし）
  - 該当オッズ帯に組み合わせが無い場合はその点をスキップ（フォールバックなし）
- **コスト**: 1レース最大500円
- **2連単は廃止**（2026-08-25）。3連単のみを予想・表示
- 神熱・見送りどちらのラベルでも同じ選出（見送りもデータ収集のため記録）


### strategy_versionの'5'→'6'（2026-09-04・統計のリセット範囲）
オッズ帯・選出方式（EV→ブレンド）を刷新したのに合わせ、`predictor.py`が保存する
`strategy_version`を'5'から'6'に引き上げた（`save_prediction`のデフォルトも'6'）。
統計は「選出方式が変わると意味が変わるもの」と「レースの実際の結果だけに基づき
選出方式と無関係なもの」の2種類に分け、前者だけをゼロから取り直す:
- **PT_RESET_FILTER（的中関連をゼロから取り直す対象）**: 的中数・的中率・
  回収率・何回に1回・現在の連続不的中数・モデル確率キャリブレーション検証・
  レース位置別的中分布・参戦ライン候補別累積成績など、「今回選んだ買い目が当たったか」
  に関わる集計。旧方式時代のデータと新方式のデータを混ぜると比較にならないため。
- **PT_ACCUMULATE_FILTER（'5'以降を積み上げ続ける対象）**: 会場別万舟ランキング、
  PT毎の平均実配当額（全レース）、万舟率など、選出方式・PTの付け方と無関係に
  「レースが実際にどうだったか」だけを見る集計。
- `web/database.py`の`_pt_v4_race_level_sql()`が`version_filter`引数でこの2種類を
  切り替える共通サブクエリ。`get_pt_score_stats()`と`get_pt_condition_breakdown()`は
  的中系とレース結果系を別々にクエリして１つの結果にマージしている（分母
  n_races_resultedも用途によって別々の値になる点に注意）。
- 今後さらに大きな方式変更をする場合は、同様にバージョンを上げて`PT_RESET_FILTER`
  （`strategy_version='X'`の形）と`PT_ACCUMULATE_FILTER`（`strategy_version IN (...)`に
  新バージョンを追加）を更新する。2026-10-16に`PT_V6_RESET_FILTER`/`PT_V5_ACCUMULATE_FILTER`
  という版数入りの名前から現在の名前にリネーム済み（今後何度バージョンが上がっても
  名前を変えずに済むように）。

### strategy_versionの'6'→'7'→'8'（2026-10-16・5点目の全面刷新＋荒れPTの配点差し戻し）
同日に2段階の変更を行った。
1. 5点目を条件ベース選出に差し替えたのに合わせ'6'→'7'に引き上げ
2. 荒れPTの配点を2026年5月当時のものに差し戻したのに合わせ、同じ考え方で続けて'7'→'8'に
   引き上げ（PT自体が変わると「的中したかどうか」に関わる全ての集計の意味が変わるため）

`/stats`ページの「新PTスコア方式」ブロック（PT値別集計・モデル確率キャリブレーション検証・
PT条件パターン別内訳・オッズ帯別成績・参戦ライン候補別累積成績・日別参戦/見送り結果）は
金色のバナーと各見出しの`new-badge`で「10/16〜本日からの新集計」であることを明示している。
会場別万舟ランキング・PT毎の平均実配当額などは引き続き'5'以降（'5','6','7','8'）を積み上げる。
`_classify_pt_pattern()`（PT条件パターン別内訳の区分判定）も新しいPTの条件文言に合わせて
A(1号艇の弱さ)/B(外艇の脅威)/C(環境条件・一般戦)の3区分に更新した（旧A〜D区分は廃止）。

### strategy_versionの'8'→'9'→revert（2026-10-19・5点目のみの変更ではバージョンを上げない）
5点目の選出方式を条件ベース(`_pick_threat_based`)から歪み検知(`_pick_edge_based`)に
差し替えた際、一旦は的中関連の集計をゼロから取り直すため'8'→'9'に引き上げたが、
ユーザーから「ここ数日間のデータが消えた」との指摘を受けて即日revertした。

**問題点**: strategy_versionは「レース単位」で1つの値しか持てない（同じレースの
1〜5点目全てに同じ値が付く）。今回は1〜4点目の選出方法は無変更だったにもかかわらず、
バージョンを上げたことで的中関連の統計（PT値別集計・オッズ帯別成績等）が丸ごとリセット
され、1〜4点目（買い目の大半・実績の大半を占める）の直近3日分のデータまで見えなくなって
しまった。「5点目だけ変えたい」という意図とバージョン全体のリセットが噛み合っていなかった。

**対応**: `strategy_version`を'8'のまま維持するようrevert（`save_prediction`の
デフォルトも'8'に戻し、`PT_RESET_FILTER`/`PT_ACCUMULATE_FILTER`も'8'までに戻した）。
revert前の短い間に'9'で保存されてしまった行は、`init_db()`に追加した一回限りの
マイグレーション（`UPDATE predictions SET strategy_version='8' WHERE strategy_version='9'`）
で次回起動時に自動的に'8'へ戻し、データを地続きに復元する（'9'の行が無ければ無害な空振り）。

**今後の方針**: 1〜4点目の選出方法自体（ブレンド方式・オッズ帯の区切り方等）を変える場合は
引き続きバージョンを上げてゼロから取り直すが、5点目のみを変える場合はバージョンを上げない
（1〜4点目の的中関連データを巻き込んで消さないため）。もし5点目だけの的中率・回収率を
前後で比較したくなった場合は、バージョンではなく別の手段（例: 変更日時でのSQL絞り込み、
または5点目専用のバージョン列を別途持たせる等）を検討する。

### モデル確率キャリブレーション検証の削除（2026-10-21）
予測確率帯（0〜1%／1〜2%／2〜5%／5〜10%／10%以上）別に予測確率と実際の的中率を
比較する`get_pt_calibration_stats()`を削除した。現在の買い目選出がオッズ帯方式
（1〜4点目は100〜250倍、5点目も歪み検知で高オッズ中心）で、個々の組み合わせの
モデル確率が構造的にほぼ全て1%未満に収まるよう選出しているため、「0〜1%」以外の
4帯は今後もほぼ永久に0件のままになる見込みで、実質的に1行分の情報しか持たない
表になっていた。テンプレート側のセクション・`app.py`のインポートと変数も合わせて削除。

使われなくなった以下のセクションと、それぞれの専用集計関数（`web/database.py`）を
完全に削除した: 日別ラベル別詳細(`get_daily_label_stats`)、等級別集計(`get_grade_stats`、
strategy_version='3'の古いデータのみ対象で既に陳腐化していた)、ヒーロー(1着)的中分析
(`get_hero_stats`)、神熱シグナル数別集計(`get_signal_stats`)、荒れPT有効性検証
(`get_pt_payout_stats`、こちらもstrategy_version='3'の古いPT体系のデータで、現行PTとは
別物になっていた)、荒れPT帯別集計(`get_pt_stats`、同じくstrategy_version='3'限定で現行PTの
データを反映しておらず「新体制になってから動いていないように見える」混乱の原因になって
いた。未使用だった`/api/pt_stats`エンドポイントも一緒に削除)、ラベル別集計

現行PTの帯別集計は「PT値別集計(1点=100円換算)」（`get_pt_score_stats`、

strategy_version='3'限定の古い集計関数はこれで概ね一掃した。今後もし同様の

バックエンド関数が`strategy_version = '3'`で絞り込んでいないか確認すること。

### 残っていたstrategy_version='3'参照を全てPT_RESET_FILTERに切り替え（2026-10-19）
`get_daily_summary`（収支グラフ）・`get_venue_detail`（会場詳細モーダル、PT帯別・
等級別の2クエリ）・`get_venue_stats`（会場別集計）・`get_payout_distribution`
（実結果3連単払戻分布、神熱/見送りのラベル分類は現行PT_MIN_SCOREの判定に基づくため
的中関連扱い）・`get_all_streaks`（連続外れアラート）の計6箇所に残っていた
`strategy_version = '3'`を全て`{PT_RESET_FILTER}`（f-string化）に切り替えた。
これで`web/database.py`内にstrategy_version='3'限定の集計関数は残っていない
（全てPT_RESET_FILTER／PT_ACCUMULATE_FILTERのいずれかを使うようになった）。

### 「参戦ライン候補別累積成績」「オッズ帯別成績」のカウント単位を点数→レースに変更（2026-10-18）
`get_pt_threshold_curve()`と`get_odds_band_stats()`は元々「賭け数」（1レースにつき最大5点の
買い目を個別にカウント）を主な単位にしていたが、1レースで複数点が同じ区分（同じPT≥Xの括り、
同じオッズ帯）に入ると水増しされ分かりにくいため、カウント単位を「レース数」に変更した
（1レースに複数点の買い目があっても1レースとして数える。的中率もレース単位: そのレースの
買い目のどれか1つでも当たれば的中としてカウント）。**回収率（ROI）の計算だけは実際に賭けた
金額＝買い目の点数×100円を正しく使う**（レース数を分母にすると実際のコストとズレるため）。
`get_odds_band_stats()`は(date, venue_name, race_no, 帯)単位でグルーピングしてから帯ごとに
集計している。`get_pt_threshold_curve()`は`_pt_v4_race_level_sql()`（レース単位の共通
サブクエリ）を使うよう変更した。

### モデル確率 vs 市場オッズ（歪み検知の検証・2026-10-18追加）
「オッズの歪み（市場の付け方のズレ）を検知して予想に活かせているか」を検証するための
統計を追加した。モデルが既に出している`prob`（的中予想確率。4エージェント合議の結果で
買い目選出にも使っている値そのもの）と、実際のオッズが暗示する確率を比較する。

- `web/database.py`に`TAKEOUT_RATE_3REN = 0.25`（3連単の控除率の概算値。厳密さより
  「常に同じ値を使って比較の軸をブラさないこと」が目的）と`get_edge_vs_market_stats()`を追加。
  市場の暗示確率 = `(1 - TAKEOUT_RATE_3REN) / odds_value`（控除率を考慮しないと
  1/オッズの合計が120通り分で約1.33になってしまい、モデル確率と対等に比較できないため）。
  エッジ = `モデル確率 / 市場の暗示確率`（1倍=市場と一致、2倍=市場の2倍強気、など）を
  5段階（0.5倍未満 / 0.5〜1.0 / 1.0〜1.5 / 1.5〜2.0 / 2.0倍以上）に区分し、各区分の
  的中率・回収率・平均モデル確率・平均市場確率を集計する。的中関連の検証なので
  `PT_RESET_FILTER`（定数なので現行PTのバージョンが上がっても自動追従）かつ
  `bet_type='3連単'`が対象
  （ライブオッズ取得時の買い目のみ市場の実際の暗示確率と一致する前提のため。
  DBに`odds_source`の区別がなく履歴オッズのみの買い目も含まれる点は注意）。
- `web/app.py`で`get_edge_vs_market_stats`をimportし、`/stats`ルートで呼び出して
  `edge_vs_market_stats`としてテンプレートに渡す。
- `web/templates/stats.html`に「オッズ帯別（1〜5点目）成績」の直後、新規セクション
  「モデル確率 vs 市場オッズ」を追加（`new-badge`で「10/18〜 新集計」と明示）。
  エッジが大きい（市場より強気）ほど実際の的中率・回収率も上がっていれば、モデルが
  市場の歪みを本当に検知できている証拠になる。関係が見られなければ、まだモデルが
  市場より正確とは言えない状態、ということがこの表から読み取れる。

### 3連単確率のキャリブレーション補正（2026-09-02追加）
上記の検証で「予測確率が実際の的中率より常に3〜4倍高い（過信）」ことが判明した。
T=2.5の温度スケーリングはMLエージェント単体の出力にしかかかっておらず（4エージェント
合成前）、残り55%の重みを持つ3エージェントは無補正のうえ、単勝確率→3連単確率への
Harville変換（3つの確率を掛け合わせる）で過信が増幅されていたと考えられる。
エージェント内部・Harville計算自体には手を加えず、`predict_race`内でHarville変換
直後の3連単確率にのみべき乗補正をかける方式にした（影響範囲を最小限にするため）。
`corrected = CALIBRATION_SCALE(0.111) * raw^CALIBRATION_EXPONENT(0.76)`。係数は
キャリブレーション実績（予測確率0〜1%→実際0.22%、1〜2%→0.5%、2〜5%→0.58%の3点）に
べき乗回帰でフィットした暫定値。3点のみのフィットなので粗く、データが増えたら
再フィットする前提。
**注意**: `get_pt_calibration_stats`はstrategy_versionでしか区切っておらず日付・
補正の有無では区切っていないため、この変更より前(未補正)のデータと後(補正後)の
データが混在する。再検証は新しいデータが十分（できれば数週間分）溜まってから行うこと。

### PT条件パターン別 内訳（2026-09-02追加）
荒れPTはA〜D区分の単純加算のため、PT4のように同じ合計値でも「A条件単独」「B+C
条件の組み合わせ」など中身が異なるレースが混在する（例: A単独は市場ミスプライシング
+4点だけで到達できてしまい頻出するため、PT4に偏りが生じやすい）。同じPT値でも
中身によって実際の的中率・配当額が違うのではという疑問への回答として、`/stats`
ページに「PT条件パターン別 内訳」を追加した。`get_pt_condition_breakdown()`
（web/database.py）が`arare_reasons`のテキスト文言からA/B/C/Dどの区分が加点に
寄与したかを判定し、パターン（例: "A"、"B+C"、"A+B+D"）ごとにレース数・平均PT・
的中率・平均実配当額(全レース)を集計する（レース単位・strategy_version='5'限定・
全期間）。DBに区分ごとのフラグ列は無いため、reasonsテキストの部分一致で判定して
いる点に注意（reasons文言の書式を変更する場合はこの判定ロジックも合わせて確認）。

## 番組表パース中の1行エラーで全体が落ちる不具合を修正（2026-10-22）
`src/collector/parser.py`の`parse_program()`は正規表現で選手データ行を1行ずつ解析
するが、2026-10-22に`b261022.txt`の一部の行で数値項目間の空白が想定と異なり、
正規表現が複数の数値フィールドを1つに連結して取り込んでしまい（例:
`"50.4110.00100.00"`）、`float()`変換で`ValueError`が発生して`parse_program()`
全体（ひいては`cmd_auto`全体）がクラッシュし、その日の予想が一切動かなくなる

`try/except ValueError`で囲み、変換に失敗した行は警告を出してスキップし、残りの
行は通常通り処理を続けるようにした（該当行の生テキストも警告に含めて原因調査
しやすくした）。

## 結果取得の再試行仕様（2026-08-31 修正）
以前は①起動時に発走済みレースを無条件で`result_fetched=True`にしていたため、
前回の実行が結果取得の途中で止まった（更新のための再起動・通信エラーなど）レースが
そのプロセスでは二度と結果を取得されなくなり、②通常リトライ（発走12分後から2分おき
最大10回=32分）を使い切ると完全に諦めていたため、ページ確定が遅れただけのケースでも
結果が永久に記録されない、という2つの原因で「予想は出ているのに結果が取得できない」
不具合が起きていた。以下のように修正:
- 起動時は`result_recorded_at`がDBに実際に記録されているかを見て`result_fetched`を判定する
  （無条件Trueをやめた）。これにより再起動のたびに未取得レースは自動的に再試行対象になる。
- 通常リトライは発走12分後から2分おき最大5回=22分後まで（`MAX_RESULT_RETRIES`）。
  それでも取れない場合は諦めずに`RESULT_RETRY_SWEEP_HOURS`（3時間）おきの見回りに
  切り替えて再試行し続ける（短時間隔で粘っても取れない理由は大抵短時間では解消しない
  ため、間隔を大きく空けて長期的に見回る方式にした。完全に諦めることはない）。
- 上記統合により、旧`_catchup_missing_results`（起動時一回限りの補完処理）は廃止。
  通常のループ内リトライが同じ役割を汎用的に果たす。

### 予想の重複バグ（2026-08-31 追加修正）
起動時の判定が「発走時刻を過ぎているか」だけを見ていたため、発走10分前〜発走前
（予想は既に出したがレースはまだ発走していない）のタイミングで再起動すると、

限定した。

### 開催中止会場の除外（2026-09-09追加・2026-09-11に無効化）
番組表(Bファイル)は前日〜早朝に作成されるため、当日の天候等による急な開催中止が
反映されていないことがある（実例: 江戸川が当日開催中止だったが番組表には通常通り

いた）という問題に対応するため、`check_venue_cancelled()`（`src/collector/beforeinfo.py`）
で各会場の公式レース一覧ページ(raceindex)を確認し、「中止」等のキーワードを含む会場を
スケジュールから除外する機能を追加した。

**しかし実際のページ文言を検証できないまま実装したため、2026-09-11に開催中の江戸川を
誤って「中止」と判定し、実在するレースの予想を丸ごと取りこぼす事故が発生した。**

はるかに深刻なため、`run_auto()`からの呼び出しを削除して無効化した

実際の開催中止ページの文言を確認したうえで`_CANCELLED_KEYWORDS`を見直すこと。

### 開催中止会場の当日限定・手動除外（SKIP_VENUES環境変数、2026-10-21追加）
自動検知を復活させる代わりに、ユーザーが実際に中止と確認した会場だけをその日限定で
手動除外できる仕組みを`run_auto()`冒頭（schedule作成の直後）に追加した。環境変数
`SKIP_VENUES`にカンマ区切りで会場名を指定して起動すると、その会場をスケジュールから
除外する（実例: 2026-10-21に江戸川が強風高波で中止になった際に使用）。
- Windowsでの使い方: そのコマンドプロンプトのウィンドウ内で
  ```
  set SKIP_VENUES=江戸川
  python main.py --mode auto
  ```
- 環境変数はそのコマンドプロンプトを閉じれば消えるため、翌日新しく開いたウィンドウで
  何も指定せずに起動すれば自動的に全会場が対象に戻る（コードを恒久的に変更する必要は
  ない。CLAUDE.mdやコード自体に特定の日付・会場をハードコードしないため）。
- `venue_day_rank`（当日の会場別順位）の計算も、除外後のscheduleを使って行われるため、
  除外した会場はその日の順位付けにも登場しない。

## 新戦略の検証: 1号艇B級×会場当日順位（2026-10-20追加）
現行PT方式（荒れPT・オッズ帯5点）とは完全に別枠で、ユーザーが考案した新しい参戦ライン
仮説を検証するための集計。条件は2つ:
1. **1号艇がB級（B1/B2、grade_num≤2）** - `_calc_race_pt`が既に判定済みで、該当すると

   この個別条件の判定自体は毎回記録される）ため、新しい列を追加せず
   `arare_reasons LIKE '%1号B級%'`で判定できる。
2. **会場別万舟ランキング（集計中・全期間ベース、`get_venue_okuma_ranking()`）を

## 当日順位1〜5位/1〜3位をSG/G1開催会場を除いた「実質」判定に変更（2026-10-24）
SG・G1開催会場は1号艇が構造的にB級になり得ないため、`venue_day_rank`（生の当日
順位）だけで上位5/3位を切ると、その中にSG/G1会場が混ざった分だけ「1号艇B級が
発生しうる会場」が実質的に減ってしまう（例: 当日順位2位がG1会場だった場合、
1〜5位の集計は実質4会場分になってしまう）という指摘に対応。

- **方式**: SG/G1会場を除いて、非SG/G1の会場がちょうど5(3)会場集まるまで
  カットオフを広げる（例: 2位がG1なら、1〜5位の判定には1〜6位を使う。1〜3位の

  当日順位」表示・「新戦略: 1号艇B級×会場当日順位」の累積カーブは生の順位の
  まま。累積カーブはN=1〜最大まで全部見る探索用の表のため、この調整の対象外）。
- **新しい列**: `predictions`・`race_preview`両テーブルに`b_class_rank5_ok`/
  `b_class_rank3_ok`（INTEGER、0/1/NULL）を追加。SG/G1除外後の実質トップ5/
  トップ3判定を、venue_day_rank_mapと同じタイミング（`src/scheduler/
  auto_runner.py`の`run_auto()`冒頭、当日最初の起動時のみ）で会場ごとに1回だけ
  計算し保存する。`venue_day_rank`と同様、同じ暦日内の再起動では計算し直さず
  既存のrace_previewデータから再利用する（`get_today_venue_ranking()`の戻り値に
  この2列も含めるよう拡張した）。
- **遡って再集計はしない方針**（ユーザー了承済み）: この機能より前のデータは
  両列がNULLのままなので、集計側は`b_class_rank{n}_ok = 1 OR (b_class_rank{n}_ok
  IS NULL AND venue_day_rank <= n)`という条件（`web/database.py`の
  `_b_class_rank_sql_clause(n)`/`_b_class_rank_ok(row, n)`で統一的に提供）で、
  新しいデータは新判定、古いデータは従来の生の順位判定にフォールバックする。
  2026-10-24以降のデータから新判定が効き始める。
- **影響範囲**（全てこの新しい判定に切り替えた）: TODAY画面の
  「本日の進行状況」のB1B2(本日1〜5位)/B1B2(本日1〜3位)、万舟カウント

  各レースカード、いずれも`b_class_rank5_ok`優先・NULLなら生の順位にフォール
  バック）、STATSページの日別サマリー3表のうち1〜5位版・1〜3位版（日付クリック

- SG/G1が絡まない通常の日は、従来の「生の順位<=5/3」と完全に同じ結果になる
  （カットオフの拡張が発生しないため）。

### FORCE_RANK_REFRESH環境変数で当日分を1回限り強制上書き（2026-10-24追加）
`venue_day_rank`・`b_class_rank5_ok`/`b_class_rank3_ok`は「当日最初の起動時の
データをそのまま再利用し固定する」仕様のため、SG/G1除外ロジックをデプロイした
当日、それより前（古いコードのまま）に起動して既に当日分のデータが固定されて
しまっていると、`git pull`して再起動しても新しい判定には切り替わらない
（固定優先のため）。この状態でユーザーから「今日は最新の状態を優先したい、
一度最新の状態にしてから再度固定してほしい」との要望があり対応した。

- `SKIP_VENUES`と同じ考え方で`FORCE_RANK_REFRESH`環境変数を追加。起動時にこれが
  立っていると、当日分のデータが既に存在していても強制的に新規計算し直す。
- さらに、`web/database.py`の`force_refresh_today_venue_values(date,
  venue_day_rank_map, b_class_eligibility_map)`で、**既に記録済みの当日分**
  （`race_preview`・`predictions`の両方。その日の朝のうちに既に予想済みの
  レースも含む）を新しい値で一括上書きする。新規に予想されるレースだけでなく
  既存データも遡って修正されるため、文字通り「今日のうちは最新の状態」になる。
- Windowsでの使い方: その日のコマンドプロンプトで
  ```
  set FORCE_RANK_REFRESH=1
  python main.py --mode auto
  ```
  と1回だけ実行する。環境変数はそのコマンドプロンプトを閉じれば消えるため、
  次に新しいウィンドウで何も指定せず起動すれば、その時点の最新の状態で
  再び固定される（この環境変数を毎回使う必要はない。ロジック変更当日の
  1回限りの救済用）。

## 実質トップ5/トップ3の判定方式をSG/G1文言検索から「1号艇B級の有無」直接判定に変更（2026-10-24）
上記のSG/G1除外ロジックを実際にデプロイしたところ、ユーザーから提供された
実データで検証した結果、**全会場が「一般」と誤判定される**不具合が見つかった
（会場別グレード判定のログで確認: 唐津がG1開催のはずなのに「一般」と表示）。
原因は、`parse_program()`（`src/collector/parser.py`）の開催グレード検出が
「ＢＢＧＮ行から60行以内で全角キーワード（ＳＧ/Ｇ１等）を検索する」方式だが、
実際の番組表データの書式に対してこのキーワード検索が機能しておらず、常に
デフォルトの「一般」になってしまっていたため。

ユーザーから「グレードの文言で判定するのではなく、実際にその会場に1号艇B級の
レースが1つでもあるかどうかで判定すればいいのでは」という提案があり、採用した。
1号艇の級の抽出自体（`_boat1_grade_by_key`、番組表の選手データ行から直接
`boat_match`正規表現で取得）は既に正しく動作していることが確認済みだったため、
この抽出結果を再利用する形に変更:

- `src/scheduler/auto_runner.py`の`_effective_cutoff()`/`_build_b_class_eligibility()`
  の第2引数を、会場別グレード文言(`_venue_meet_grade`、廃止)から会場別
  「1号艇B級のレースが実際にあるか」のbool値(`_venue_has_b_class`)に変更。
  `_venue_has_b_class`は`_boat1_grade_by_key`（当日の全レース分の1号艇の級）を
  会場ごとに集計し、`B1`/`B2`が1つでもあれば`True`とする。
- この方式はSG/G1に限らず、どんな理由であれ1号艇B級のレースが1つも無い会場を
  同じように検出して除外するため、グレード文言の書式に依存しない、より汎用的で
  頑健な判定になった（番組表の書式差異の影響を受けない）。
- `_boat1_grade_by_key`の計算を「朝一プレビュー」ブロックから当日順位の
  カットオフ判定ブロックへ移動した（両方で使うため、計算順序を入れ替えた）。
- コンソール診断ログも「会場別グレード判定」から「会場別1号艇B級レース有無」に
  変更（`_venue_has_b_class`の中身をそのまま出力）。
- `PT_MIN_SCORE`計算等で使っていた`meet_grade`列自体（PTの「一般戦」加点判定等）
  は変更していない。今回変更したのはあくまでトップ5/トップ3のカットオフ判定の
  入力元だけ。

## 本日の進行状況（全会場通し）に万舟の発生頻度（1/X.XXX）を表示（2026-10-24）
- TODAYページの「本日の進行状況（全会場通し）」ウィジェットの4行（万舟 / 万舟(B級) /
  万舟(B級×1〜5位) / 万舟(B級×1〜3位)）それぞれに、回数表記の直後に
